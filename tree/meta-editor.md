# Node: can an editor keep learning how to edit?

Parent: [PR #49](https://github.com/manojbajaj95/cl/pull/49) (model-guided edits), sub-question 4.

Question: can an editor keep learning *how to edit*, from gradient descent's own weight changes and from the outcomes of its own edits, while the model it edits keeps changing?

## Root cause

**What an editor knows about editing is written in the base model's current coordinates, and every edit moves those coordinates.** That includes the editor's own edits and every SGD step. An editor maps (input, model state) to ΔW. Once an edit is accepted, the model state it learned on is gone, so its training data goes stale as fast as it is used. Every current approach handles this by learning to edit **offline, against a fixed base and a fixed edit distribution, and then freezing the editor**. None of them keeps learning at deployment.

Three gaps follow from this, and each one blocks a deployed editor that learns:

1. **Its own outcomes are too sparse to learn from.** An edit returns one accept/reject bit or one score for a ~10⁶–10⁷-dimensional action. So WSP loops use the outcome to *select* edits, not to *learn editing*: the verifier does the learning, and the editor at round 5 is no better at editing than at round 1.
2. **Gradient descent's ΔW is a dense teacher, but a dirty one.** The ΔW of an SGD step mixes the content of the update with path noise (batch order) and gauge (function-preserving rescalings, permutations). It is also written in the same drifting coordinates. Fitting an editor to SGD steps is learned optimization, and learned optimizers still fail to generalize outside their meta-training tasks and horizons.
3. **An editor that does learn online is itself a continual learner, with no retention mechanism.** Learning edit type B degrades edit type A one level up (meta-forgetting). Every retention method we have protects the base, not the editor.

**The missing object is a base-invariant, outcome-labelled edit record:** a (state, edit, outcome) triple in coordinates that stay meaningful after the base has moved on. Without it, neither SGD's diffs nor the editor's own outcomes add up to lasting editing skill.

### Evidence from papers

| Paper | Finding relevant to the root cause |
|---|---|
| RLEdit [2502.05759](https://arxiv.org/abs/2502.05759) | Hypernetwork editors (MEND, MALMEN) "tend to fail after only around 100 edits" because of "their incompatibility with LLM parameters that dynamically change during the editing process". The fix trains the hypernetwork by RL over whole edit sequences, offline, then freezes it. |
| HiEdit [2604.11214](https://arxiv.org/abs/2604.11214) | Hierarchical RL picks the layers per edit and gains +8.48% over RLEdit. Still meta-trained offline and frozen. |
| MEND [2110.11309](https://arxiv.org/abs/2110.11309), MALMEN [2311.04661](https://arxiv.org/abs/2311.04661) | Editors that take *the gradient* as input, so they already "learn from gradient descent". But they are trained once per base model and do not adapt as that model changes. |
| Self-WSP [2611.28833](https://arxiv.org/abs/2611.28833) | Random search with the same budget matches self-editing on GSM8K, and the model "shows little understanding of the edits it makes". |
| SelfWrite [2611.29513](https://arxiv.org/abs/2611.29513) | Over 5 generations of self-edits, Qwen3.8-27B gate accuracy goes from 73.95% to 76.45%. "The editor improves together with the model" only as a side effect: no signal trains the editing skill itself. |
| WeightLoop [2611.07319](https://arxiv.org/abs/2611.07319), HypoLoop [2611.23718](https://arxiv.org/abs/2611.23718) | Editors whose plans are revised from accumulated feedback, but only within one task. The LLM editor is fixed, and what it has learned does not carry to the next task. |
| VeLO evaluation [2310.18191](https://arxiv.org/abs/2310.18191); ELO [2607.06772](https://arxiv.org/abs/2607.06772) | A learned optimizer trained with 4000 TPU-months still needs per-problem tuning and is no faster than tuned baselines. Meta-training is "biased toward short-unroll learning", so learned optimizers fail on long horizons. |
| Automated CL [2312.00276](https://arxiv.org/abs/2312.00276); SRWM [2202.05780](https://arxiv.org/abs/2202.05780) | Self-referential nets learn their own in-context CL algorithm, but it is meta-learned offline over a task distribution and does not keep improving at deployment. |
| Learning trajectories leave traces [2611.24782](https://arxiv.org/abs/2611.24782) | Final weights still encode their initialization and the order of training. So SGD's diffs are informative, and they also carry path-specific content an editor should not copy. |
| Distributions over weight updates [2610.01934](https://arxiv.org/abs/2610.01934) | Generated updates transfer across queries, so the hypernetwork learns reusable structure in how a model should adapt. It is trained offline on a fixed base. |
| Learning through discernment [2611.23716](https://arxiv.org/abs/2611.23716) | A small model fine-tuned each night on its own judged outcomes improves and then decays over a simulated year. Learning from your own outcomes is fragile when the labels are lopsided (Spearman ρ = −0.81 between the share of failures among lessons and the outcome). |

Earlier nodes say the same. PR #49 found that raw-weight choosers depend on the gauge. The self-describing-weights node ([PR #53](https://github.com/manojbajaj95/cl/pull/53)) found that a *shared frame* is what makes writes portable. The edit-simulator node ([PR #63](https://github.com/manojbajaj95/cl/pull/63)) found that an edit's effect depends on (W, data, path), not on W alone. This node adds time: even a good frame is wasted if the editor cannot keep learning in it.

## Raw ideas (no self-filtering)

Each entry gives the mechanism, why it is new, and the cheapest first test. Every test includes a **retention check on two levels**: the base model's invariant probe set and an **editor invariant set**, a fixed panel of old edit problems with known solutions that the editor must still solve. Known overlaps are flagged for the reviewer.

Shared toy testbed, unless stated otherwise: the PR #49 MLP (4 × 128), fed a stream of linear-teacher remaps that mix recurring and new shift types; the editor is a small MLP or transformer; 3–5 seeds.

1. **Shadow-SGD apprenticeship with a self-retiring teacher.** On every incoming batch, a shadow copy takes the SGD step. Before seeing that step, the editor predicts it. The loss is the *function-space* error between the two on probes (KL or MSE of outputs), not the weight-space error. Once the editor's predicted error on a shift type is below τ, it replaces SGD there, so SGD runs only on what is new. *New:* learned optimizers are meta-trained offline. Here the editor is distilled from the optimizer online, at deployment, and the teacher retires itself one shift type at a time. *First test:* fraction of steps the editor takes over, and the editor's regret vs SGD over the stream. *Retention:* base probes plus the editor invariant set for the first shift types. *Risk:* learned-optimizer meta-generalization failure (VeLO).

2. **Behavior coordinates for edits, with a compiler back to weights.** Store every edit, SGD's or the editor's, as its effect on a fixed probe basis, e = J_probe·ΔW. The editor learns and remembers only in e-space. A data-aware compiler (least squares with key covariance C, ROME-style) maps e back to weights in *whatever the current base is*. *New:* the editor's knowledge is then defined by behavior and survives base drift. The edit-simulator node uses effect fingerprints to *predict* edits ([PR #63](https://github.com/manojbajaj95/cl/pull/63) #11, #21), not as the coordinates in which an editor keeps learning. *First test:* train the editor at base step t, apply it at t + 100 SGD steps; compare weight-space and e-space editors on efficacy. *Retention:* protected probes in the compiler's null space.

3. **Hindsight relabelling of failed edits.** A failed edit still produced *some* behavior change. Relabel it as a successful edit for the behavior it actually produced, and train the editor on it (HER for weight edits). One outcome bit becomes a dense supervised example. *New:* no editor uses its failures as positive examples. *First test:* an online editor over 1k edit attempts with and without relabelling; edits needed to reach 80% efficacy. *Retention:* damage of later edits on base probes, plus the editor invariant set.

4. **Learn SGD's mistakes, not its steps.** After the fact, joint training (or retraining with knowledge of later data) gives the step that would have been ideal: ΔW*. The editor learns only the residual ΔW* − ΔW_SGD, as a correction added to every future SGD step. *New:* the editor is a learned lens on the optimizer's systematic errors (forgetting directions, overshoot on rare classes) rather than a replacement for it. *First test:* a stream with recurring tasks; forgetting with the correction vs EWC and OGD at equal compute. *Risk:* meta-learned regularizers ([2510.08968](https://arxiv.org/abs/2510.08968)).

5. **One language for editing the editor and the knowledge.** The editor lives inside the model as a block that the same compiler writes. Improving the editor is then just one more edit and gets the same retention protection as any knowledge edit. *New:* it closes the loop so meta-forgetting is handled by the base's own retention machinery. *Risk:* close to SRWM and SelfWrite; new only if the editor block is protected by the same null-space compiler. *First test:* the editor's skill on edit type A after it has been trained on type B, with and without compiler protection.

6. **Complementary learning systems for the editor.** A fast editor learns online from recent outcomes. A slow editor is distilled from it on a replay buffer of (state, edit, outcome) triples, with a function-space anchor. *New:* CLS one level up, where it targets meta-forgetting. *First test:* an edit-type curriculum (fact edits, then format edits, then fact edits again); the slow editor's competence when type A returns. *Retention:* the editor invariant set by design. *Risk:* CLS itself is known.

7. **Editor invariant set as a standing gate.** Every update to the editor must keep its accuracy on a fixed panel of old edit problems, each a (base state, target, verified solution). The metric is "edit regret over time". *New:* it is the invariant probe set for the learner of learning. *First test:* run ideas 1, 3 and 6 with and without the gate and measure editor forgetting. *Risk:* this is an evaluation primitive more than a method.

8. **A forgetting operator learned from outcomes.** From pairs (SGD step on new data, measured damage on old probes), learn a damage predictor per direction and use it to project future SGD steps. *New:* GPM and OGD compute their projectors from stored gradients. This one is *learned from observed damage* and can generalize to old tasks it has no stored gradients for. *First test:* retention vs GPM at equal memory, on old tasks held out from the projector's training.

9. **An editor that learns in context from an edit log.** The editor is a transformer whose context holds the last K tuples (state summary, edit code, outcome). It improves in context with no weight updates, so it cannot forget within the window; the log is compacted into its weights periodically. *New:* ICL over weight edits. ACL ([2312.00276](https://arxiv.org/abs/2312.00276)) does ICL over tasks, not over edits. *First test:* editor regret vs log length K; editor retention after compaction.

10. **SGD path variance as an edit denoiser.** Run SGD on the same data in k batch orders. The shared part of the k ΔWs is the content; the disagreement is path and gauge. Train the editor only on the shared part, or on a learned denoiser. *New:* the optimizer's own variance defines what an edit should contain. *First test:* an editor trained on the 4-run consensus vs on single runs; generalization to new shifts. *Retention:* consensus edits should damage fewer probes.

11. **Revert rate: gradient descent as the critic of edits.** After an edit, keep training normally on mixed data for k steps and measure how much SGD undoes it (the projection of later ΔW onto −ΔW_edit). An edit SGD fights conflicts with the data; one it leaves alone is consistent with the data. Use the revert rate as a free edit-quality label. *New:* the optimizer becomes a dense, label-free edit critic, with no held-out evaluation. *First test:* Spearman of revert rate with true retention damage and with generalization, against an edit-norm control. Gate: it must beat the norm.

12. **Edit to pre-empt the optimizer.** Train the editor so that the gradient norm on the incoming stream is small right after its edit: write now what SGD would learn anyway. *New:* the step is conditioned on the shift signature, not on past weights. *Risk:* weight nowcasting (Introspection, Sinha et al. 2017; WNN, Jang et al. 2023). *First test:* total steps to a target loss, with retention probes.

13. **A dictionary from shift signature to edit.** Key memory by a signature of the *change in the data* (Δ input covariance, Δ label marginals). The value is the e-space edit that SGD converged to after that shift. When a known shift recurs, apply the edit at once; when it is new, run SGD and add an entry. *New:* the editor remembers "how this model should respond to this kind of change", indexed by the change, not by task id. *First test:* recurring shifts at random magnitudes; adaptation speed on recurrence vs task-id adapters and replay. *Retention:* base probes after each lookup.

14. **Edit commutation table from SGD.** Compare SGD on A→B and B→A to learn which edit types commute. The editor uses the table to schedule or batch edits. *Risk:* the ledger killed bounded-delay reordering (order effects are O(η²)). Kept raw; it is new only if edits are large and non-local. *First test:* whether the non-commutation of large rank-1 edits is predictable from e-codes.

15. **A frame learned online so SGD steps become predictable.** The editor learns a function-preserving reparametrization of the base (per-layer permutation and scale) in which SGD's next ΔW is as predictable as possible, and updates that frame as the stream goes on. *New:* the frame is learned from the optimizer's diffs, not fixed by statistics ([PR #63](https://github.com/manojbajaj95/cl/pull/63) #13 whitening; [PR #53](https://github.com/manojbajaj95/cl/pull/53) anchors). *First test:* R² of next-ΔW prediction in the learned frame vs the C^{1/2} frame vs raw weights. *Retention:* function is preserved by construction.

16. **Active edit experiments.** The editor sometimes picks edits that tell it most about its own outcome model, not edits that are best for the task, and reverts them after measuring. *New:* the editor runs experiments on its own learning. *Risk:* close to PR #49 #2 (world model from random edits); new is the active, online choice. *First test:* outcome-model error per real evaluation, active vs random probing edits.

17. **Make the base predictable to the editor.** Add an auxiliary loss so that the base's own SGD updates are predictable by a small fixed editor (co-adaptation). *New:* Edit-Ready Training ([2611.26408](https://arxiv.org/abs/2611.26408)) prepares networks for closed-form edits; this prepares them for *amortizing their own optimizer*. *First test:* fraction of steps the editor takes over and base accuracy, with and without the aux loss. *Retention:* invariant probes.

18. **Editor knowledge as optimizer state.** The editor does not write ΔW. It writes a preconditioner (Shampoo-like) that SGD uses, and SGD's resulting ΔW then trains the editor. *New:* a closed loop between the learned editor and the optimizer state, so the editor improves SGD and SGD keeps teaching the editor. *Risk:* SM25 Lamarckian optimizer state (flood triage, 4-tier). *First test:* steps to a target on recurring shifts with a static vs a loop-trained preconditioner.

19. **"Should have edited earlier" labels.** When a later SGD step fixes an error first seen at time t₀, label the state at t₀ with that ΔW, mapped to e-space, as the edit it should have made then. *New:* hindsight from future gradients back to the moment of failure, so the editor learns to act on the first sign. *First test:* a stream with delayed labels; cumulative loss with an anticipatory editor vs SGD.

20. **A universal edit prior pooled across models.** Collect SGD ΔWs from many small models' responses to the same shifts, map them into behavior coordinates (idea 2), and train one prior. *New:* gradient descent from many models teaches one editor. *First test:* train on seeds 1–9, apply zero-shot to seed 10, against a direct SGD step of the same size. *Retention:* seed 10's probes.

21. **Edits with learned half-lives.** The editor predicts how long each edit will survive later training and either over-writes to compensate or schedules re-application. *New:* persistence has been *measured* ([2511.05852](https://arxiv.org/abs/2511.05852), [2610.07510](https://arxiv.org/abs/2610.07510)) but not *learned and used* by an editor. *First test:* Spearman of predicted vs actual half-life against an edit-norm control.

22. **Inverse RL over the optimizer's trajectory.** Treat SGD's trajectory as an expert demonstration in weight space and infer the reward it implicitly optimizes (loss plus implicit regularizers such as min-norm). The editor optimizes the inferred reward *plus* a retention term SGD ignores. *New:* the editor learns what SGD values rather than what it does, so it can depart from SGD exactly where SGD ignores retention. *First test:* does the inferred reward recover the known loss plus the min-norm bias on linear regression? Then measure retention on the MLP.

23. **SGD vs editor tournament with mutual teaching.** On each batch both propose an update; a short probe evaluation picks the winner. If SGD wins, the editor distills its step. If the editor wins, its edit becomes a prior target for the next SGD steps. *New:* teaching goes both ways between the optimizer and the editor. *First test:* the editor's win rate over the stream, and base retention compared with SGD alone.

24. **Self-play edit curriculum with SGD as the oracle.** A proposer generates edit targets just past the editor's skill; the editor tries them; SGD (many steps) provides the reference solution. *New:* asymmetric self-play applied to editing skill. *First test:* growth of editor skill vs random targets at an equal SGD budget. *Retention:* editor invariant set.

25. **Tracking the rotating update subspace.** SGD updates over a stream lie in a low-dimensional subspace that rotates slowly. The editor tracks it online and also predicts its *rotation* from the shift signature, then edits within the predicted subspace. *Risk:* low-dimensional gradient subspaces are known (Gur-Ari et al. 2018); new is predicting the rotation. *First test:* fraction of next-ΔW energy inside the predicted subspace vs the last-k subspace.

## Deeper sub-questions, ranked by chance of a new primitive

1. **What representation of an edit stays meaningful after the base it was written for has changed?** Behavior coordinates with a compiler back to weights, or a frame learned from SGD's own predictability. This is the missing object named in the root cause, and every other branch needs it. Ideas 2, 15, 20.
2. **Can gradient descent act as a free, dense critic and teacher of edits, through revert rate, path-variance consensus, hindsight from later steps and inverse RL, so the editor gets labels without held-out evaluations?** This turns the optimizer from a competitor into the editor's supervisor. Ideas 3, 10, 11, 19, 22.
3. **Can an editor take over from SGD online, one shift type at a time, and what does meta-forgetting look like when it does?** This is the direct test of the node question and needs the editor invariant set as its metric. Ideas 1, 6, 7, 9, 13, 23.
4. **Should the editor learn SGD's mistakes (forgetting directions, residuals, preconditioners) instead of its steps?** A cheaper target with a direct retention payoff. Ideas 4, 8, 18, 21.
5. **Can the base be trained so that its own updates are predictable, making editing amortizable by design?** Ideas 12, 17, 25.

Ideation only: no experiments were run for this node.
