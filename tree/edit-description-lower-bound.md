# Node: how small can an edit description be and still stay valid under later training?

Parent: [PR #96 edit-invariant-description](https://github.com/manojbajaj95/cl/pull/96), sub-question 1 ("characterize the minimum edit message by the requests a receiver cannot safely conflate").

**Question:** Is there a lower bound on the size of an edit description that stays valid while the model keeps training, and what does it imply for continual learning?

**Short answer from a CPU probe:** yes. The bound is the log of the number of requests the receiver can tell apart along its whole future trajectory, not at install time. The bits a description saves by leaning on the model's current behaviour are a loan that later training calls in. Under unstructured drift the loan is repaid in full, so the description grows back to the full intent specification. It stays short only for what training leaves invariant.

## Root cause: the parent's bound is computed against a frozen receiver

PR #96 defines a confusion graph over a fixed family of receivers at installation: two requests may share a message on a receiver if they demand the same result there. A short message works because the receiver's own state is *side information*. In the shipping example, a receiver whose express fee already equals the target can treat "add $1 to all shipping" and "set standard to $6" as the same instruction, so one message serves both. That is zero-error coding with decoder side information (Witsenhausen 1976; Alon and Orlitsky 1996, characteristic graphs).

Continual learning breaks the one assumption this needs: the side information stays still. After installation the receiver trains on new tasks. A stored edit description is decoded again whenever the edit is re-applied, re-verified, consolidated, repaired after interference, or transferred to the next checkpoint. Each time, the receiver's state is different. Two requests that coincided on the install-time model can diverge on a later one. The message that merged them is then ambiguous: it decodes to a valid result for one of them and a wrong one for the other, and nothing in the message shows this.

So the parent's minimal message is minimal *because* it borrows the most from a state that CL guarantees will move. Minimality at install time and durability under training pull in opposite directions. Probes, witnesses, teaching sets and checksums that are sized against the current model inherit the same defect. The relevant object is the union of the confusion graphs over every state the receiver will be in while the description must stay valid.

### The bound

Fix a request family R, an observation language, and the receiver's trajectory f_0, f_1, ..., f_H under later training. Write r(f) for what request r demands of receiver state f. A zero-error description valid for all t ≤ H must give different messages to r and r' whenever r(f_t) ≠ r'(f_t) for some t. The smallest number of messages is therefore at least

  χ(G_0 ∪ G_1 ∪ ... ∪ G_H) ≥ max_t χ(G_t),

where G_t is the confusion graph at step t. When admissibility is exact equality (no don't-cares), the graph is an equivalence relation and this number is exact: the count of distinct tuples (r(f_0), ..., r(f_H)). With don't-cares it becomes a coloring problem with hyperedges (PR #96, card 1). Three consequences:

1. **The bound is monotone in the horizon.** It can only grow as training continues. As H → ∞ it tends to the bound computed over the set of states reachable by training, which equals the full intent specification log₂|R/≡| unless training preserves some invariant of the receiver that R can see.
2. **The saving is a loan.** Install-time saving = log₂|R/≡| − log₂χ(G_0). Repayment by step H = log₂χ(∪_{t≤H} G_t) − log₂χ(G_0). The saving that survives forever is exactly the information R shares with the *invariants* of training.
3. **It holds for any encoder.** It holds even for an oracle that knows the future trajectory, so a real encoder that does not know it needs at least as much (the worst case over plausible trajectories is larger still).

### CPU probe: [`tree/probes/edit_description_bound_probe.py`](probes/edit_description_bound_probe.py)

The receiver is a lookup table f with 6 inputs and values in Z_4. Requests are `set c on S`, `add c on S`, and contextual `remap v→c on S` (rewrite only the inputs of S whose current value is v, like "every standard-shipping fee"). There are 1,197 requests, all semantically distinct over 64 random receivers, so the full intent costs 10.23 bits; an explicit post-edit table costs 12 bits. One training step rewrites m random inputs (free drift), shifts every value by a constant (a gauge invisible to the request language), or rewrites inputs outside a protected set P = {0,1,2}. The table gives mean bits over 200 trajectories (exact count, about 20 s on CPU).

| Drift | H=0 | H=1 | H=4 | H=16 | H=32 | Loan repaid at H=32 |
|---|---|---|---|---|---|---|
| free, m=1 | 8.07 | 8.22 | 8.53 | 9.23 | 9.71 | 1.64 of 2.16 bits (76%) |
| free, m=2 | 8.06 | 8.34 | 8.85 | 9.71 | 10.10 | 2.04 of 2.17 bits (94%) |
| shift gauge | 8.07 | 9.06 | 9.88 | 10.23 | 10.23 | 100% (46% after one step) |
| free outside P | 8.06 | 8.21 | 8.47 | 8.84 | 8.95 | 0.89 bits (41%); limit with P invariant 8.98 |
| free m=1, message also stores f_0 on 2 inputs | 12.07 | 12.17 | 12.38 | 12.84 | 13.10 | storing raw anchors already costs more than the full intent |

What this shows (in a toy, under exact zero-error validity):
- Side information saves about 2.2 of 10.2 bits at install. Ordinary drift takes most of that back within a few dozen steps, and a drift the request language cannot see takes half of it back in one step.
- When training leaves part of the state untouched, the saving levels off at the value predicted from the invariant (8.95 measured at H=32 vs the 8.98 limit). **Durable compression equals information about the invariants of training.**
- Storing the side information verbatim ("anchors") is the naive fix, and it is strictly worse than sending the full intent. A useful fix stores *only* what the description depends on, or states the edit in terms that later training leaves invariant.

This is a toy. It says nothing yet about how fast real SGD drift repays loans, or which invariants a transformer's training actually has. Those are the sub-questions below.

### What it implies for CL

- **Forgetting is a loss of decodability, not only a loss of weights.** Every compressed memory of the past is decoded with the current model as side information: an edit description, a lesson, a replay index, a regularizer anchor, a teaching set, an LoRA meant to be re-applied. It can become wrong while every stored byte is intact. The bound prices this effect.
- **Retention constraints compress worst of all.** "Keep f(x) as it is" costs zero bits at install (the receiver already holds the answer) and its full value after any drift on x. Without invariants, keep-constraints cannot be compressed below an explicit record, so replay-like storage is forced by information, not by habit.
- **The memory budget of a CL system is set by its future drift, not by the size of the edit.** A long-lived system needs a rate–drift function: bits needed as a function of how much training the description must survive.

## Raw ideas (no self-filtering)

Every first test is a CPU toy or the probe above extended. Unless the drift itself is what is being varied, compare arms at equal stored bits (including shared vocabulary), equal decoder queries and equal training. "Retention" always means old-task behaviour and earlier edits measured against the pre-edit model's ground truth, reported separately from new-edit success.

1. **Side-information loan ledger.** *Mechanism:* every stored description records the bits it borrowed from the current model (install-time saving), and the learner tracks how much each training step calls in (exact in toys, a sampled estimate on probes in real models). *Why new:* forgetting metrics measure outputs or weights; this measures how decodable the stored specifications still are. *First test:* in the probe, check that repaid bits predict which descriptions decode wrongly at the next re-application better than step count. *Retention:* correlate repayment with old-task accuracy on a tiny MLP stream; it must beat a constant guess.
2. **Rate–drift function R(Δ).** *Mechanism:* define the minimal bits needed for a description to stay valid through a training budget Δ (steps × LR, or a KL ball around the model) as a new CL law, analogous to rate–distortion. *Why new:* no CL work bounds memory size by future drift. *First test:* sweep drift rate and horizon in the probe and on a 2-layer MLP with real SGD drift; check whether bits collapse onto one curve in Δ. *Retention:* measure old-task error at each Δ alongside.
3. **Invariant-stated descriptions.** *Mechanism:* rewrite each request in coordinates training leaves unchanged (relative values, orderings, ratios, protected inputs), so that the loan is never called. *Why new:* PR #96 card 6 picks units for portability across *models*; here the invariants are chosen by the *training dynamics* of one model. *First test:* re-express requests relative to a reference input under the shift gauge; bits should stay at the H=0 value. *Retention:* the old behaviour on the reference input must not be distorted to keep the invariant.
4. **Precoding against your future self.** *Mechanism:* the encoder samples plausible future models (short training rollouts on likely next data) and codes against the union of their confusion graphs. *Why new:* dirty-paper coding (top-10 #5) uses known interference; this codes for a distribution of unknown future decoders. *First test:* in the probe, sample 4 rollouts and measure validity on held-out true trajectories vs an install-only code at equal bits. *Retention:* the rollouts must not be the training itself; check old tasks on the actual future.
5. **Layered (Heegard–Berger) edit descriptions.** *Mechanism:* a base layer decodable by every reachable future model, plus a refinement layer valid only near the current one; the refinement expires and is dropped or refreshed. *Why new:* successive refinement (PR #56 #12) layers by fidelity, not by how long each layer stays valid. *First test:* split probe codes into durable and expiring parts and count total bits over a stream with periodic refresh. *Retention:* after a refinement expires, the base layer alone must not damage protected cases.
6. **Dependency set of a description.** *Mechanism:* compute the smallest set of receiver behaviours whose values the decoding depends on, and protect only those during later training. *Why new:* EWC/replay protect the edit's outputs; this protects the side information that keeps its specification decodable. *First test:* the probe's protected-set arm shows a plateau; compare protecting the dependency set with protecting the same number of random or edited inputs. *Retention:* old tasks outside the dependency set may drift; check whether this costs them.
7. **Dependency checksum (loan-default detector).** *Mechanism:* store a short hash of the dependency set's install-time values; a mismatch at decode means the loan was called, so abstain and fetch more bits. *Why new:* behaviour CRCs (PR #56 #44) check fixed prompts; this checksum is derived from each description's own confusion structure. *First test:* detection rate vs bits for random-prompt CRCs of equal size in the probe. *Retention:* false alarms trigger refreshes; count the extra writes and their damage to old tasks.
8. **Interactive repayment (intent escrow).** *Mechanism:* the authority keeps the full intent; the model stores the short description; on a detected default it asks for exactly the bits needed to resolve the new conflicts. *Why new:* edit refresh re-sends the whole edit; Orlitsky's results suggest interaction can cost far less than one-shot in the worst case. *First test:* count authority bits under on-demand vs install-time full spec over 32 steps in the probe. *Retention:* the stretch between default and repair is a window of wrong behaviour; measure the old-task error in it.
9. **Retention constraints are incompressible under drift.** *Mechanism:* prove (toy) and measure that "keep f(x)" descriptions cost 0 bits at install and their full value after any drift on x, so replay-like records are forced unless training has invariants. *Why new:* a converse for why replay keeps winning (ledger pattern: "ties replay at equal budget"). *First test:* add keep-requests to the probe and plot their bits vs H. *Retention:* this idea is about retention itself; report the bits per retained case.
10. **Decodability horizon scheduling.** *Mechanism:* predict each description's horizon H* (when its loan is mostly called) and re-encode it just before, instead of fixed-interval refresh. *Why new:* spaced repetition schedules by recall failure; this schedules by predicted ambiguity before any failure is visible. *First test:* equal refresh budget, horizon-scheduled vs uniform vs failure-triggered in the probe stream. *Retention:* wrong decodes on old edits between refreshes.
11. **Loan-preserving training.** *Mechanism:* a regularizer that penalizes changes to the confusion classes of stored descriptions (a differentiable surrogate: values on their dependency sets) rather than to all old outputs. *Why new:* it protects only what the specifications need, so plasticity elsewhere is untouched. *First test:* tiny MLP, equal regularizer strength vs EWC and equal-byte replay of edit outputs. *Retention:* old-task accuracy, plus new-task gain to show plasticity is kept.
12. **Saving × lifetime trade-off law.** *Mechanism:* conjecture that install-time saving times expected lifetime is bounded by a quantity set by drift entropy, so a description cannot be both very short and long-lived. *Why new:* a waterbed-style constraint (cf. top-10 #1) for memory size instead of forgetting spectrum. *First test:* sweep request families and drift kernels in the probe; check whether the product stays bounded. *Retention:* not applicable to the law itself; report old-task error at each operating point.
13. **Invariant-limit predictor.** *Mechanism:* predict a description's long-run cost from the information R shares with the invariants of training (the probe's 8.98-bit limit matched the 8.95-bit H=32 value). *Why new:* turns "what survives training" into a computable quantity for specifications. *First test:* estimate invariants of a small MLP's SGD (e.g. outputs on inputs whose gradients are orthogonal to the new task) and predict which edit descriptions stay valid. *Retention:* the same invariants should predict which old tasks are retained; compare to a constant guess.
14. **Loan cascades between edits.** *Mechanism:* a description can borrow from behaviour that an earlier edit installed; when that edit drifts, every later description depending on it defaults together. *Why new:* write-skew (top-10 #3) concerns joint invariants of updates; this is dependency chaining between specifications. *First test:* chain 5 edits in the probe where each borrows from the previous; measure cascade size vs independent descriptions. *Retention:* earlier edits' success after one is perturbed.
15. **Gauge-aware request languages.** *Mechanism:* find the drift directions the request language cannot see (the shift gauge erased 46% of the saving in one step) and add exactly enough vocabulary to see them. *Why new:* gauge issues in weights are known (PR #53, PR #59); this is a gauge between the *description language* and the training dynamics. *First test:* add a "relative to x_ref" operator and measure bits under shift drift. *Retention:* old behaviours on x_ref.
16. **Loan-aware data selection.** *Mechanism:* during later training, down-weight samples whose gradients move the dependency sets of many descriptions. *Why new:* replay selection targets interfering samples for outputs, not specifications. *First test:* tiny MLP, select from a candidate pool by dependency-set movement vs by gradient interference (GEM-style). *Retention:* old tasks and earlier edits at equal new-task progress.
17. **Self-consistent descriptions (fixed points).** *Mechanism:* keep only descriptions whose decode→re-encode loop returns the same description under the current model; track whether the fixed point moves continuously during training. *Why new:* round-trip consolidation (top-10 #7) checks content survival; this checks the specification's own stability. *First test:* in the probe, count descriptions that remain fixed points across H vs those whose loop jumps. *Retention:* edits re-derived from jumped fixed points must not overwrite old behaviour.
18. **Average-case vs zero-error gap.** *Mechanism:* compare the zero-error bound with an ε-error (Shannon, conditional entropy) bound; CL may accept rare wrong decodes for a large saving. *Why new:* it gives a bit price for "probably still valid" memory. *First test:* compute both in the probe for ε ∈ {0.01, 0.05}. *Retention:* the rare wrong decodes should be audited on protected cases specifically.
19. **Fork-union bound for fleets and merges.** *Mechanism:* a description shared by k forks of a model must be valid on the union of their trajectories; the bound grows with k as with horizon. *Why new:* fleet memory (PR #56 #21) sends syndromes against one receiver's current memory. *First test:* 1, 2 and 4 forks with independent drift in the probe. *Retention:* each fork's own old tasks after receiving the shared description.
20. **Depth-placed side information.** *Mechanism:* make descriptions depend on behaviours computed by the layers that later training moves least, and measure the repayment rate per layer. *Why new:* layer choice for edits targets efficacy; this targets durability of the specification. *First test:* a 3-layer MLP; descriptions decoded through early vs late features; measure repayment under fine-tuning. *Retention:* old-task accuracy is unchanged by where descriptions read from; check it.
21. **Learned drift kernel to price new descriptions.** *Mechanism:* fit the empirical behaviour-transition statistics of the learner from past updates and, before installing an edit, choose the description form with least expected lifetime cost. *Why new:* edit simulators (PR #63) predict immediate effects; this predicts specification lifetime. *First test:* fit on the first half of a probe stream, price the second half; must beat a constant guess. *Retention:* forms chosen for durability must not trade away old-task protection.
22. **Training-trajectory quotient of requests.** *Mechanism:* call two requests equal iff they decode the same along every training trajectory in a declared family, and learn the quotient with L*-style queries. *Why new:* the Nerode quotient (top-10 #2) uses later edits as continuations; this uses later training. *First test:* count classes vs trajectory-family size in the probe. *Retention:* class membership should predict old-task outcomes after training.
23. **Description-validity certificate under a training budget.** *Mechanism:* bound the reachable behaviour set for a budget (Lipschitz or NTK ball) and certify that a description remains unambiguous inside it. *Why new:* certified edits (PR #85, obligation compile) certify installation now, not specification validity under future training. *First test:* linear model with exact reachable sets vs empirical trajectories. *Retention:* the certified ball should also bound old-task drift; check it.
24. **Forgetting score = decode error of stored specifications.** *Mechanism:* report CL forgetting as the fraction of stored descriptions (edits, lessons) that now decode to the wrong behaviour, alongside accuracy. *Why new:* accuracy misses silent specification failures that appear only at the next re-application. *First test:* in a small stream, find cases where accuracy is unchanged but decode error rises. *Retention:* this is a retention metric; validate it against later accuracy drops (must beat step count as predictor).

## Deeper sub-questions, ranked by chance of a new primitive

1. **Is there a rate–drift function for real SGD, and does its limit equal the information shared with training's invariants?** The probe shows the limit in a toy with a planted invariant. The open question is whether real training has measurable invariants (for example, function on gradient-orthogonal inputs) that set durable description size, and whether bits collapse onto one curve in a drift budget. This would be a new CL law: memory size set by future drift. Ideas 2, 12, 13, 23.
2. **Can a description protect only its dependency set and still stay valid, at less plasticity cost than protecting outputs?** This turns the bound into a method: a new primitive object (the dependency set of a specification) that regularizers, replay and schedulers can target. Ideas 6, 7, 11, 16.
3. **Can interaction beat the one-shot bound by a large factor, making cheap on-demand refresh the right CL memory protocol?** Orlitsky-type gaps between one-shot and interactive worst-case communication suggest so; measure it with a real learner. Ideas 8, 10, 14.
4. **Are retention constraints provably incompressible under drift, so replay is forced, and is the gap to edit constraints what makes edits cheaper than keeping?** A converse would explain a recurring ledger pattern (replay ties) and point to the invariants as the only way out. Ideas 9, 18, 24.
5. **Which request languages are gauge-complete for a given training process?** Find the smallest vocabulary extension that stops a drift direction from calling loans in one step. Ideas 3, 15, 20.
