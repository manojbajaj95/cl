## Merge proposals

**ACF1. Test whether one compatibility shim really replaces many adapter ports.** Parts: HS01 two-sided adapter-branch shim, HS02 branch versus base path, HS03 rank scaling, HS04 ledger versus generic inputs, HS16 residual failure predictor, HS21 matched controls, HS22 fleet break-even, HS23 consecutive releases, HS24 toy-to-release validation, HS25 unseen-adapter scaling, HT08 shared shim, PL5-10 held-out effects. *Mechanism:* Fit one read/write bridge for a synthetic fleet and hold out whole adapter families. Increase fleet size while recording the smallest shim rank that reaches the target; distinguish preservation of unknown adapters from interpolation among seen ones. Compare ledger prompts with equally sized generic prompts and test whether residual mismatch predicts failures before using it for routing. *New:* One shim is a fleet-level object only if its size grows sublinearly while held-out adapters retain performance and the serving overhead does not consume the porting savings. *First test:* On toy release sequences compare branch-only and base-path shims with per-adapter ports and a generic-input bridge. Test the source's 90% per-adapter ReLoRA accuracy bar on unseen adapters and report worst-decile retention, rank, and break-even after inference cost.

**ACF2. Compare adapter-blind compatibility with learning what the next fleet will need.** Parts: HS05 adapter-blind fit, HS06 fleet-blind fit, HS07 compatibility loss, HS08 pooled fragility, HS15 probes and steering, HT18 base-level fragility, HM17 repeat-offender gate, NP4-13 response to future evidence. *Mechanism:* Compare bridges fitted with no adapter access using approved synthetic ledger summaries against generic calibration and adapter-aware fitting. Score read-only probes separately from adapter writes and benign steering. Use repair history to train the next base only if HM17 finds previously repaired inputs regress at least twice the base rate; otherwise keep the compatibility study without pooled-history training. *New:* An adapter-blind bridge should preserve what a future specialization can do rather than simply matching activations on current prompts. A history-based compatibility loss earns credit only if it helps a new fleet. *First test:* Hold out toy adapter families and a later generation. Compare fleet-blind, adapter-blind and adapter-aware bridges and a matched vendor-side loss; report held-out read and write performance and the cost of each information regime.

**ACF3. Bound where an upgrade changes behavior without freezing intended improvements.** Parts: HS09 compatibility frontier, HS10 declared change envelope, HS17 loss of upgrade gains, HS18 defensive robustness audit, HS19 wanted changes, HT09 authorized upgrade negotiation, NP5-26 protected future reads. *Mechanism:* Declare intended changes before fitting. Audit held-out decisions outside the envelope and check improvements inside it on both base-only and adapter traffic. For defensive robustness, use benign inconsistent synthetic ledger entries and compare bounded per-adapter influence with ordinary averaging. Report leakage bounds for the declared fixture and workload only. *New:* A shim that preserves old behavior by undoing the upgrade is not compatible in the useful sense. Report both retained improvement and unintended change. *First test:* Change a verified synthetic conversion convention while preserving unrelated tasks. Compare a branch shim, a global shim and per-adapter ports at matched information; report out-of-envelope changes, intended gains and worst-decile retention.

**ACF4. Treat a chain of shims as a temporary migration path, not permanent fleet state.** Parts: HS11 chained shims, HS12 retire or port, HS13 mixed native and old adapters, HS14 co-loaded old adapters, HS20 cross-family boundary, AL3-09 composed maps, NP4-21 composition under shared lineage. *Mechanism:* Compare chaining with one direct bridge and a native port after a second release. Test old and native adapters in the same synthetic co-loads and keep lineage so a shared adjustment is not applied twice. Define retirement by observed failures or total serving overhead, not by the number of releases alone. *New:* A bridge that passes every adapter alone may fail when old and new updates interact. Co-load behavior, not single-adapter validation, decides whether the migration path can be kept. *First test:* Run two toy upgrades with layout and vocabulary changes and leave some adapter pairs unseen. Compare stacked and direct bridges with native ports on mixed co-loads, retained gains and end-to-end cost.

**ACF5. Move a fleet across releases without making every adapter inherit the same failures.** Parts: HS01 two-sided adapter-branch shim, HS02 branch versus base path, HS03 rank scaling, HS04 ledger versus generic inputs, HS16 residual failure predictor, HS21 matched controls, HS22 fleet break-even, HS23 consecutive releases, HS24 toy-to-release validation, HS25 unseen-adapter scaling, HT08 shared shim, PL5-10 held-out effects, HS05 adapter-blind fit, HS06 fleet-blind fit, HS07 compatibility loss, HS08 pooled fragility, HS15 probes and steering, HT18 base-level fragility, HM17 repeat-offender gate, NP4-13 response to future evidence, HS09 compatibility frontier, HS10 declared change envelope, HS17 loss of upgrade gains, HS18 defensive robustness audit, HS19 wanted changes, HT09 authorized upgrade negotiation, NP5-26 protected future reads, HS11 chained shims, HS12 retire or port, HS13 mixed native and old adapters, HS14 co-loaded old adapters, HS20 cross-family boundary, AL3-09 composed maps, NP4-21 composition under shared lineage. *Mechanism:* Keep compatibility local to the adapter branch when possible, compare a shared shim with per-adapter fallback, and independently measure the behaviors the release was meant to change. Evaluate unseen families, protected neighbors and mixed co-loads throughout. Keep the HM17 gate for pooled repair history; a failed gate does not block ordinary compatibility tests. *New:* A shared bridge should lower total migration cost while preserving the new base's gains and making its failure cases visible enough to route to native ports. *First test:* Run a proposed synthetic release sequence with an intended rule change, previously unseen adapters and independently held-out co-loads. Compare the shared bridge, direct per-adapter ports and release-side training at matched access and budget. Report held-out performance, leakage and lifecycle cost.

## LoRA prior-art check: PR #407

[MUSCLE](https://arxiv.org/abs/2407.09435) already targets negative flips with per-task compatibility adapters, and [MKP-Adapter](https://arxiv.org/abs/2609.16875) provides adapter-only backward compatibility in the embedding setting. The [Universal Activation Bus](https://arxiv.org/abs/2608.09521) already shares activation-based tools via an encoder–decoder pair per model. Compare a fleet shim against these ideas and against per-adapter LoRA-X, Trans-LoRA and ReLoRA: the claim is sublinear capacity for preserving unseen adapters' read and write behavior, not alignment alone. [Declared change envelopes](https://arxiv.org/abs/2611.04192) already provide a statistical framework for outside-envelope leakage; the proposed combination must also preserve allowed improvements and old-adapter co-load behavior. Evaluate total cost against [UpgradeBench](https://arxiv.org/abs/2608.20918) retain, port, refresh and retrain policies. This is a targeted baseline comparison, not a priority claim.
