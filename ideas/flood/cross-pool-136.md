## Merge proposals

**ACD1. Move a behavior to a cheaper representation only if it can still be amended.** Parts: HT01 checked migration, HT02 demotion to prompt, HT03 traffic-based consolidation, HT04 round-trip loss, HT05 split across tiers, HT06 co-load validation, HT25 load-aware serving, HC20 tested exceptions, NP4-19 future-operation equivalence. *Mechanism:* Try prompt, steering and adapter versions of the same synthetic rule. Require the full ledger, agreement among independent rebuilds on held-out inputs and retention in affected co-loads. Demote only when the cheaper version passes, and reserve a withheld exception to check whether the round trip preserved what a later amendment needs. *New:* Two tiers are not interchangeable just because today's outputs agree; the test is whether old exceptions and the next authorized correction still work under the cheaper representation. *First test:* Migrate a synthetic formatting rule with rare exceptions to a lower tier after a base upgrade and back again. Compare fixed-tier and split-tier storage at matched target gain, report co-load failures, amendment success and serving cost.

**ACD2. Move the compatibility work from each adapter to one release.** Parts: HT07 compatible base upgrade, HT08 shared shim, HT09 upgrade negotiation, HT10 per-ledger pin, HT11 fleet release gate, HT24 longitudinal cost, HM23 authorized supersession, NP4-21 shared lineage. *Mechanism:* Compare a one-time compatibility phase or a single shared shim with retaining or porting every adapter alone. Use verified provenance to separate intentional rule changes from regressions; do not pin obsolete behavior by default. Test adapter families and co-loads withheld from fitting. *New:* A shared compatibility update saves work only if it generalizes to specialists not represented in its fitting ledger without blocking improvements authorized by their owners. *First test:* Upgrade a toy base across several releases with fixed small adapters. Compare a shared shim and a compatibility-trained base to per-adapter transfer, refresh or retraining with equal evidence. Report upgrade work, target gain and failures on held-out adapter families.

**ACD3. Use disagreement between passing rebuilds to ask useful questions.** Parts: HT12 underdetermination queries, HT13 tier choice, HT14 regression prediction, HT15 compatibility measure, HT21 matched controls, HT22 representative held-out traffic, HM05 rebuild agreement, AL31 unresolved choices, PL5-10 held-out effect families. *Mechanism:* Group disagreements among independent ledger-passing rebuilds on a synthetic workload. Treat them as candidate omissions, not proof that the specification is incomplete: rerun with independent builders and test whether a verified answer resolves the group. Evaluate regression prediction against repair history and ordinary confidence signals. *New:* A disagreement is useful if one verified answer resolves many future cases or identifies a tier that remains unreliable outside the ledger. *First test:* Compare clustered disagreement, random and confidence-based queries at equal verified-answer budgets, then test on sealed task families and a representative mixture of toy co-loads.

**ACD4. Predict repeat regressions before retraining and keep the acceptance check independent.** Parts: HT16 preemptive writes, HT17 cross-domain fragility, HT18 base-level fragility map, HT19 necessity by omission, HT20 independent acceptance of proposed self-edits, HT23 HM17 gate, HM17 repeat-offender assay, NP5-26 protected future reads. *Mechanism:* Run HM17 first on held-out update streams: require previously repaired inputs to regress at least twice the base rate before proceeding with HT16–HT19. If it passes, test whether fragility transfers across synthetic domains and whether omitting a ledger entry brings its regression back. If it fails, drop the history-based variants and retain only the independent ledger acceptance check for proposed changes. *New:* An entry can prevent a repeat failure without being a reliable predictor by itself. Distinguish protection caused by the entry from selection based on history. *First test:* Compare preventive constraints and post-hoc repair at equal information and compute on toy adapters with shifting rules. Keep a sealed benign retention check for proposed updates and measure target gain, negative flips and ledger size.

**ACD5. Carry a verified behavior specification through serving, migration and repair.** Parts: HT01 checked migration, HT02 demotion to prompt, HT03 traffic-based consolidation, HT04 round-trip loss, HT05 split across tiers, HT06 co-load validation, HT25 load-aware serving, HC20 tested exceptions, NP4-19 future-operation equivalence, HT07 compatible base upgrade, HT08 shared shim, HT09 upgrade negotiation, HT10 per-ledger pin, HT11 fleet release gate, HT24 longitudinal cost, HM23 authorized supersession, NP4-21 shared lineage, HT12 underdetermination queries, HT13 tier choice, HT14 regression prediction, HT15 compatibility measure, HT21 matched controls, HT22 representative held-out traffic, HM05 rebuild agreement, AL31 unresolved choices, PL5-10 held-out effect families, HT16 preemptive writes, HT17 cross-domain fragility, HT18 base-level fragility map, HT19 necessity by omission, HT20 independent acceptance of proposed self-edits, HT23 HM17 gate, HM17 repeat-offender assay, NP5-26 protected future reads. *Mechanism:* Keep the ledger separate from any one representation, make authorized changes explicit and test each move on independent rebuilds, held-out examples and affected co-loads. Use disagreement to request evidence, not to assume permission to change behavior. Require HM17 before any history-based prevention; a failed gate leaves ordinary independent acceptance checks. *New:* The ledger earns its role only if it supports reversible moves between tiers and lowers fleet-wide upgrade or repair cost without hiding failures on new specializations. *First test:* Run a proposed harmless synthetic fleet through a base upgrade, a tier change and a later amendment under load. Compare the combined approach with independent porting, LoRA-only rebuild and fixed retention probes at matched bytes, examples and compute.

## LoRA prior-art check: PR #405

[Cortex](https://arxiv.org/abs/2610.20399) consolidates context into parametric updates, while [CSPD](https://arxiv.org/abs/2611.27376) distills experts into composable soft prompts. Neither is a baseline to dismiss: test bidirectional migration and later amendments, not consolidation or prompt compression alone. [UpgradeBench](https://arxiv.org/abs/2608.20918) compares retaining, porting, refreshing and retraining specialists across releases. [Backward-compatible training](https://arxiv.org/abs/2003.11942) already trains new visual embeddings to work with old ones; a shared language-model shim or compatible base must show that it preserves previously unseen adapters at lower total cost than per-specialist policies. [SEAL](https://arxiv.org/abs/2506.10943) already generates its own update data and directives; the ledger proposal adds a testable acceptance criterion, not evidence that regressions are impossible. The repair-history arm also compares against fixed-probe KLOD, replay and positive-congruent training at matched access and cost. This is a targeted baseline comparison, not a priority claim.
