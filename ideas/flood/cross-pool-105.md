**ORX2. Keep the lesson valid through representation and state changes.** Parts: L9W05 sequence witnesses, L9W06 passive fixture scheduling, L9W07 stable input schema, L6W12 representation rotation, SD2-09 distinguishing suffix, LW10 interface contract. *Mechanism:* Store an approved synthetic sequence witness with its input schema and starting-state precondition. Use already available authorized examples first and check a fresh held-out continuation after a representation change. A version change that invalidates the precondition calls for revalidation, not auto-rebuilding. *New:* A recovery lesson can distinguish sequential behavior while remaining independent of the backbone's hidden coordinates. *First test:* Use two mock formatting workflows with identical single-input responses but different permitted sequence outcomes. Compare one-input fixtures, stored trajectories and versioned sequence checks under a feature rotation.

**ORX3. Train only the parts of a skill that can stand alone as code.** Parts: L9W10 region budget, L9W11 sparse predicates, L9W12 logic sidecars, L9W13 dense-to-crisp schedule, L9W14 observable bottleneck, L9W15 route fuzzy skills elsewhere, L9W16 monotone constraints, L9W17 extraction fidelity, L8W12 localized compilability, D3-12 checked dependency frame. *Mechanism:* Apply extraction-oriented training only to a new module with observable inputs and declared invariants. Compare early and delayed regularization, checking actual extracted behavior on held-out compositions rather than using sparsity as proof. Leave fuzzy or dependent behavior in the learner where the standalone checks do not apply. *New:* Compilation becomes a measurable objective without forcing the dense backbone or the fuzzy residual to imitate a rule list. *First test:* Mix exact synthetic predicates and ambiguous cases. Compare post-hoc extraction, whole-model regularization and isolated compilable heads on task quality, code size and verified fidelity.

**ORX4. Reclaim a module only after its replacement and later reuse are checked.** Parts: L9W18 isolated excision, L9W21 re-compilable recovery, L9W22 approved edit checks, L8W17 update-matched audit, L8W22 scratch round trip, CR29 versioned relearning. *Mechanism:* Verify standalone equivalence on the declared scope, then remove the candidate module in scratch state and test an unrelated update and a fresh amendment. Test recovery from an independent approved packet when the checker is absent. If the policy changes, validate the new rule and retire the obsolete packet rather than recovering stale answers. *New:* A compile-and-remove step is useful only if it frees measurable learning capacity and leaves a valid recovery path that can itself be maintained. *First test:* Use an editable toy checker whose replacement adds one approved exception. Compare module deletion, replay and checked round trips under equal update work, including unavailable-checker and stale-packet arms.

**ORX5. Check simultaneous recovery in compatible outage scenarios and measure both stored code and common dependency cost. Keep independent coverage where a shared bank would make otherwise separate obligations fail together. *New:* The same simplification may shrink code and training packets, but only a joint audit can tell whether that saving creates a new dependency. *First test:* Cross overlapping and independent predicates with shared and separate checker outages. Compare independent modules, an unchecked shared bank and verified factoring at matched coverage and total work.
