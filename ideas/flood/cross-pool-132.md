## Merge proposals

**ABZ1. Port a contract by testing the next amendment.** Parts: HC05 native recompilation, HC06 probe alignment, HC07 component-level fallback, HC08 refusal to port, HC09 tokenizer migration, HC11 chained upgrades, HC27 equal-information controls, HL21 recompilation, NP07 byte-prefix update conjugacy, NP4-13 future evidence response. *Mechanism:* Align on the same contract prompts, then check a later amendment in a shared raw-string readout. Record which components pass without a rewrite and which fail because the target cannot express the claim. Compare acceptance at matched coverage so refusing difficult cases cannot inflate the score. *New:* A port can preserve today's responses and still change how tomorrow's correction behaves; a component-level certificate should predict that difference. *First test:* Port a toy formatting rule across two tokenizer changes, then issue an unseen exception. Compare direct recompilation, functional transport fit on contract prompts and matched-data retraining; hold out amendment families.

**ABZ2. Keep the reason for a repair when the patch goes stale.** Parts: HC12 port with counters, HC13 concentration assay, HC14 handwritten repair, HC15 retract or counter, HC16 neighbour-specific routing, HC17 stale counters, HC19 training constraints, HC20 tested exceptions, HC21 contract-aware retraining, HL15 spillover repair, NP5-26 future-revealed interference. *Mechanism:* Use component ablations to decide whether spillover is concentrated before proposing a narrow repair. Carry the protected behavior and target floor into the next training round, not the old counter's numbers. Recheck both after retraining and regenerate the counter only if needed. *New:* Repair becomes reusable knowledge if the same named neighbor stays protected after a later ordinary update without sacrificing target gain. *First test:* Train a synthetic spatial rule that interferes with a nearby distance rule. Compare retraction, a matched-rank counter, spectral repair and equal-example replay or KL; after retraining measure whether the repair still holds and how many new counter parameters are needed.

**ABZ3. Make co-load rules expire when the assumptions behind them change.** Parts: HC01 contract checker, HC18 shared counter, HC22 co-load conflict detection, HC23 versioned blame, HL12 composition checks, NP4-21 common-ancestor composition. *Mechanism:* Represent a shared repair as one component with explicit preconditions, not an additive patch copied into each adapter. Check actual composed sets after revisions and recheck any set whose overlap or ancestor changed. *New:* A shared correction can be deduplicated without assuming that passing pairwise tests guarantees compatibility for larger sets. *First test:* Use small synthetic domain adapters with benign overlaps. Compare deduplicated repair, per-adapter repair and full subset checking before and after a revision; count missed regressions and overcorrections.

**ABZ4. Compress a contract only if it survives independent tests of later changes.** Parts: HC02 minimal contract, HC03 extract from weights, HC04 mutation testing, HC10 compile on demand, HC24 retention prediction, HC25 contract convergence, HC26 independent tests, HC28 cost ledger, HL20 retained regression tests, NP4-19 equivalence under future operations, PL5-10 held-out effects. *Mechanism:* Minimize stored claims and tests against a declared set of revisions and upgrades, not just reconstruction today. Use benign test mutations and a separate evaluator to check the omitted material, and account for cold-start rebuild cost. *New:* This distinguishes a compact specification from a growing audit log: later edits should need fewer extra tests without losing predictive power. *First test:* Fit contracts on a synthetic rule stream. Compare full and compact contracts, a flat test suite and adapter checkpoints at matched storage or access; measure missed regressions after withheld revisions and count new tests per revision.

**ABZ5. Keep the contract as the part that learns.** Parts: HC05 native recompilation, HC06 probe alignment, HC07 component-level fallback, HC08 refusal to port, HC09 tokenizer migration, HC11 chained upgrades, HC27 equal-information controls, HL21 recompilation, NP07 byte-prefix update conjugacy, NP4-13 future evidence response, HC12 port with counters, HC13 concentration assay, HC14 handwritten repair, HC15 retract or counter, HC16 neighbour-specific routing, HC17 stale counters, HC19 training constraints, HC20 tested exceptions, HC21 contract-aware retraining, HL15 spillover repair, NP5-26 future-revealed interference, HC01 contract checker, HC18 shared counter, HC22 co-load conflict detection, HC23 versioned blame, HL12 composition checks, NP4-21 common-ancestor composition, HC02 minimal contract, HC03 extract from weights, HC04 mutation testing, HC10 compile on demand, HC24 retention prediction, HC25 contract convergence, HC26 independent tests, HC28 cost ledger, HL20 retained regression tests, NP4-19 equivalence under future operations, PL5-10 held-out effects. *Mechanism:* Compile numeric components on each base, keep claims and protected observations in a versioned contract, and carry only repairs that predict future behavior. Separate missing target capabilities, failed transport and new spillover so each has its own fallback. Use independent tests for target gain, untouched tasks and previously accepted rules. *New:* The contract earns persistence only if it lowers cumulative repair and migration cost relative to the same evidence kept as ordinary replay or regression tests. *First test:* Run a proposed toy stream with one upgrade, a co-load revision and a rare amendment. Compare functional transfer plus replay with versioned contracts and flat tests; match evidence and report target gain, neighboring retention and cumulative evaluation and rebuild cost.

## LoRA prior-art check: PR #401

[Theseus](https://arxiv.org/abs/2602.12952) and [Ariadne](https://arxiv.org/abs/2610.32581) already transport task effects by matching activations without training; give them the same contract-region prompts. The additional bar here is whether checked component claims predict the effect of a later amendment, with rejection compared at matched coverage. [SPECTRA](https://arxiv.org/abs/2611.10279) already demonstrates low-rank post-training restoration for a specific behavior, and [KLOD](https://arxiv.org/abs/2608.27839) protects non-target distributions in knowledge editing. The repair proposal must preserve a named benign neighbor at a fixed target-gain floor after retraining, with equal-example controls. [From LoRA to Language](https://arxiv.org/abs/2611.09454) already recovers skill text from adapters, and [Audit Before You Merge](https://arxiv.org/abs/2611.10684) already checks provenance and probes retention in composition. Text recovery and auditing alone are not the proposed advance: the question is whether a versioned testable contract predicts later repair and compatibility better than the same evidence as a flat test suite. This is a targeted comparison, not a priority claim.
