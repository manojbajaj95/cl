# How to run the continual-learning playground

Start with [probe-before-write](frontier-scan.md#1-probe-before-writing-identify-the-shift-then-update-only-the-affected-mechanism). The first decision is whether a few interventions reveal **which learned module to keep**, not whether a larger model learns a changing benchmark. Keep the other bets as alternatives, not simultaneous GPU projects.

## Novelty check before scale

1. Write a one-sentence claim, the closest baseline that could disprove it, and an explicit counterexample. For probe-before-write: ordinary action distributions can alias two shifts; distinguishability requires an available anchor; even when identifiable, adaptation may give no advantage over a fixed mode library.
2. Search arXiv, OpenReview and Scholar/Semantic Scholar across adjacent vocabulary (e.g., active fault diagnosis, sensor/actuator isolation, modular causal dynamics, recurrent domain adaptation, online system identification, and compositional world models). Trace cited and citing work and inspect methods and artifacts, not just abstracts. Record dated queries, nearest papers' assumptions, what they already demonstrate, and the proposed difference. Repeat before the first full run and before submission. If a close paper already answers the claim, redesign the question rather than renaming the method.
3. Make the smallest diagnostic test that separates explanations and reproduce the strongest relevant baseline on it. Have a second reviewer try to make the proposed method unnecessary. Freeze the held-out stream generator, metric, hypothesis, budget and acceptance rule in a timestamped manifest before evaluating it.

## Common stream contract

- **Predict, score, then update.** An event carries time, observations, and any actions, evidence or feedback available at that time. A method predicts before scoring or seeing withheld targets, and updates only from permitted feedback. For active tests, charge exploratory transitions and report online errors at common evaluation checkpoints using separate, unrevealed trajectories. Do not expose boundaries, regime IDs, later corrections, held-out labels, or future retrieval items. Keep oracle variants separate.
- **Hold out sequences and underlying factors.** Tune on development streams; test on unseen seeds, entity graphs or module combinations, not shuffled rows. Include recurrences after long delays, abrupt and gradual changes, and no-change controls. Eval does not mutate the learner; make state persistence and explicit resets part of the protocol.
- **Track three cohorts.** Maintain a fixed invariant probe set, a time-indexed current-target set, and an episodic prior-regime/historical probe set. Report invariant retention (delta from pre-stream score), revision latency (events from shift to a predeclared target, marking misses as censored), and reacquisition on recurrence. Use time-averaged prequential loss or rollout error, not just final accuracy. For classic task sequences add forgetting and backward/forward transfer; do not count intentional corrections to stale targets as forgetting. For retractions, include downstream state equivalence and relapse.
- **Budget the whole system.** Use the same initial checkpoint and stream, tune baselines on the same number of development runs, and report quality vs. training/inference FLOPs, examples, wall time, peak VRAM, and persistent bytes (index, logs, slots, optimizer, and adapters). Charge synthetic teacher calls, retrieval context, speculative forks and simulator probes, including probe energy where applicable. When different resources cannot all be matched, report tradeoff curves rather than a single claimed winner.
- **Treat the stream as the replicate.** Use at least five paired, independent held-out streams per seed-sensitive pilot setting; pair baseline and candidate on initializations and stream seeds. Report individual traces and paired confidence intervals over streams, not over questions or steps. Use pilot variance to size later study; freeze the test size and inference procedure before the full run. Treat a small noisy interval as inconclusive, not a win.

## Start small; add external validity second

| Stage | What to run | Gate |
| --- | --- | --- |
| 0 · CPU | Analytic simulator: passive aliasing, stable-anchor pulse, broken anchor, exact known-mode filter. Test no future access and state persistence. | Recover chance in symmetry control and predicted signal with a stable anchor. If the diagnostic signature fails, inspect the setup before training. |
| 1 · One GPU | ~0.1–2M world model and held-out DM Control shift schedules. Frozen and full adaptation + replay, modular passive, equal-energy random probes, known-mode active diagnosis, in-context conditioning, and shift-label oracle. For language alternatives: 0.5B backbone, same frozen/sequential/replay baselines plus strong retrieval and method-specific controls from the [scan](frontier-scan.md#ranked-research-bets). | Use the scan's thresholds: primary paired point estimate meets the minimum effect, CI excludes no benefit, and the lower CI for the retention delta stays above the allowed loss. If effects disappear against matched budgets, if the oracle has little headroom, or if the strongest baseline explains the result, stop or change the claim. No cluster to resolve a failed mechanism. |
| 2 · Replicate then scale | Add a second independent environment/observation family for world models; for language, use a small, timestamped [TiC-LM](https://arxiv.org/abs/2504.02107) slice (continual pretraining), [MemoryBench](https://arxiv.org/abs/2510.17281) (feedback memory), or [ERASE's evolving QA](https://arxiv.org/abs/2406.11830) (revisions), selected according to the claim. Use a fixed downstream retention suite appropriate to the base checkpoint. Deduplicate across time splits where possible and document plausible base-model contamination. | Replicate mechanism **and** budget benefit on an independent setting; include the ablations, failure regimes, and matched strong baseline. A benchmark win without the predicted interaction is not a mechanism claim. |

## Tooling and compute

- Start with PyTorch + deterministic Python/NumPy simulators; use Gymnasium/DM Control for the next world-model test and Transformers/PEFT plus a pinned LM evaluation harness for a language pilot. Use a small shared stream runner with timed prediction/update APIs and structured per-event output, not one bespoke harness per method. Unit-test chronology, query budgets, deterministic replay (where claimed), and metric behavior against an explicit oracle. Pin model/data revisions, split manifests, source/checkpoint hashes and seeds.
- Write local JSONL metrics and metadata for each run; optionally mirror summaries to W&B or MLflow. Store commands, resolved configs, commit IDs, package versions, machine/GPU type and checkpoint hashes. Record profiler-measured cost, run state, and errors; keep datasets/checkpoints in persistent storage outside git. Preserve failed and negative runs. Produce figures from saved artifacts to make rerunning plots independent of training.
- Estimates in the scan are **total per pilot**, not measured timings; plan for a single 24 GB GPU for modest models and profile one baseline and one candidate before scheduling all runs. Charge runtime as measured minutes per seed × methods × seeds × settings, including evaluation, plus explicit tuning allowance. Do not reserve a cluster yet. If a pilot and an independent replication pass, parallelize seeds/configs before considering distributed training. A planning envelope for independent runs is 4 methods × 5 seeds × 2 settings × 8 GPU-hours/run = 320 GPU-hours, or ~40 hours on 8 GPUs at perfect utilization before tuning; replace every assumption with profiler data before requesting capacity. Use a larger model only if the scientific question requires a scale test.

The first artifact beyond these notes should be a reproducible **Stage 0** runner with passive, anchored, and broken-anchor controls. Keep the result (including a null) and a decision log. If Stage 1 shows shift identification but not reuse, move to counterfactual sparse rollback rather than escalating compute.
