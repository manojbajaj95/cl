# Rebuild skills after their original model is gone

**Updated verdict: no-go for scaling either tested method.** The follow-up [release-chain pilot](pilot/README.md#follow-up-held-out-release-chains) found that diversity improved mean skill accuracy, but no selection variant reliably lowered harmful admissions at the fixed coverage target. At the larger budget the best estimate was 75.0% harmful accepted releases vs. 88.5% for random int8; both paired intervals for that difference included zero. A procedural pivot compiled revised and revoked skills perfectly across compatible coordinate changes, but two demonstrations per primitive with the same affine prior were equally sufficient at the same bytes. Neither experiment establishes a new capability over its strongest baseline. The plan below records the original hypotheses and scaling gates, not a recommendation to reserve GPUs.

**Research question.** Can a capability survive a sequence of backbone replacements and be independently revoked when its training data, source checkpoint, and source editor are all gone? The target is not a better merge score on one pair of checkpoints. It is a new operating regime: one live backbone, a fixed total retained-state budget, unannounced inference tasks, and explicit permission to decline unsupported migrations.

## Three directions, and what survived the pilot

1. **Static, reversible compilation from behavior contracts.** Retain output changes on positive probes and constrain the patch on negative probes; recompile and sum additive patches at each release. Clean accuracy dropped 19.1 points even on a function-preserving coordinate change because the *source composition itself* was bad. Independent release performance deteriorated further. Reject a single ungated final-head patch family for these tasks; an all-reject gate is not a solution. This does not rule out nonlinear or earlier-layer static patches.
2. **Tested: counterfactual witnesses for migration and removal.** Retain selected positive, negative, and overlap probes to reconstruct a conditional weight program on future checkpoints and diagnose when not to install it. Conditional rebuilding recovers much of two easy skills, but the original audit misses failures and the router misfires on unregistered inputs. In the follow-up, choosing high-contrast probes alone was worse than uniform replay; class-balanced diversity helped mean accuracy without clearing the safety gate. The follow-up held routing fixed to isolate witness selection; it did not establish open-set routing or end-to-end revocation.
3. **Tested pivot: procedural skills rather than example caches.** Learn or write a program that regenerates the skill from a compact rule/grammar and compiles it into the replacement representation. [Tracr](https://arxiv.org/abs/2301.05062) gives known target semantics, but [WeightCode](https://arxiv.org/abs/2611.25476) already installs rule-derived and successive skills. Our affine transducer supports revision and explicit revocation through width and basis changes, but affine induction from two saved demonstrations is exactly as good: the recorded rule and demonstration values are invertible encodings of the same information. A future procedural bet would need a preregistered family in which a known grammar yields cheaper identifying evidence or generalization than *grammar-aware* replay, and a learned successor representation, not just a known coordinate map. This is rule versioning and recompilation after source retirement, not the sibling scan's replay of learned memory write dependencies.

## Hypothesis and proposed method

**H1:** At matched total bytes, install/search budget, and inference cost, retaining probes that distinguish competing explanations of a skill will reduce **harmful accepted actions at matched nontrivial coverage** versus keeping random examples and teacher outputs. This should hold on unseen lineages and overlapping tasks, without a teacher checkpoint at upgrade time. A harmful action includes a skill/retention violation, collateral damage after revoke, or a patch firing on unsupported inputs. A false reject costs an otherwise deployable upgrade; report it separately.

At acquisition, use the source and a public or generated candidate pool. For each skill, store indexed probe inputs (or generator seeds), quantized teacher responses, and comparisons with the skill enabled and disabled. Reserve sealed audit witnesses that the installer never sees. Unlike replay sampling by label or entropy, actively select contrasts where plausible local fits or candidate routers disagree: include pairs whose outputs should diverge under an intervention and pairs whose output should stay fixed. Build negatives from neighboring skills, paraphrases, mixed tasks, no-trigger inputs, and explicit abstention cases. No hidden test prompts in generation or selection. The follow-up tests disagreement between the source specialist, unmodified source, and sibling patch. It does not test the full combination of contrastive audit sets and open-set routing.

On a new release, generate native low-rank patches from the retained targets, with a fixed install budget. Begin with a residual last-layer solve; compare output fitting and selected block-level intervention fitting on the same data. Score new patch/router combinations on separate audit witnesses and route to the unmodified release when the input is unsupported. Do not overwrite the original witness with each migration. If budget or coverage is exhausted, declare which capability cannot be migrated, rather than silently evicting it. Count recovery costs including retaining an approved previous deployment during staging; for already retired sources, the no-legacy fallback is the current base, with lost capabilities recorded.

Revocation removes a named branch from the installed model without refitting its siblings. Compare forwarding to base for revoked inputs versus rerouting; **freeze the router and use base fallback** for the primary test to avoid revocation implicitly changing routing priority. Check each surviving capability before/after and compare accepted install→revoke with the counterfactual run where the skill was never installed. Exact equality outside the revoked branch holds when a fixed hard router never selects that branch and computations share no mutable state; it does not prove correct scope assignment or unlearning.

**Why witnesses might help and what is impossible.** In a fixed linear readout, if two programs differ by a vector in the nullspace of the retained feature rows, they agree on every retained fit probe. If that vector is not null on future evaluation features, they can differ there. No estimator using only those probes can distinguish the two on that evidence; logging probes is not a certificate. Construct such collisions explicitly and test whether contrast selection can expose them or reliably decline deployment. Use this result to delimit claims, not to assume a novel theorem or distribution-free guarantee.

**Closest prior art:** [Ariadne](https://arxiv.org/abs/2610.32581) and [GRAFT](https://arxiv.org/abs/2611.18638) already carry specialization effects or route adapters across architectures. [Heirloom](https://arxiv.org/abs/2611.00650) distills while the old model is available; saving its outputs in advance is an obvious no-source baseline. [UpgradeBench](https://arxiv.org/abs/2608.20918) already gates migration on held-out evaluations. [GRACE](https://arxiv.org/abs/2211.11031) and [reversible routed LoRA](https://arxiv.org/abs/2603.11239) already isolate edits, and [MDM-OC](https://arxiv.org/abs/2507.20997) targets selective reversal. Neither routing, teacher snapshots, gating, nor ridge itself is the novelty. The paper-level claim would be that **interventional probe selection preserves identifiable, selectively revocable behavior over source-free release chains at a fixed total budget**, with empirically measured failure boundaries. This combination has not been established by the reviewed work; novelty remains to be tested and rechecked.

## Evaluation and decisions

| Phase | What to run | What could disprove it |
|---|---|---|
| CPU mechanistic tests | Multiple split/permuted/rotated digits streams, nonlinear features, deliberately colliding and compositional inputs, multiple arrival/removal orders. Add function-equivalent gauges, short continuations, independent models, and destructive bottlenecks. Compare random replay, disagreement-only, and counterfactual witness selection at fixed bytes; bound adequate rank and exact counterfactual behavior in the linear case. | No clear gap between random replay and counterfactual selection at any honest coverage, or the method cannot detect known collisions better than simple distance/entropy. |
| Vision checkpoint chains | CIFAR-100 class sequences plus CIFAR-C-like domains, withheld corruption pairs and severe shifts. Train/release checkpoint families with seed/width/feature-drift controls; evaluate both task-free and domain-ID-oracle conditions. Keep source, migration, and final labeled evaluation costs separate. | Gains disappear after separating source and target lineages, or task-ID oracle explains them entirely. |
| Language release chains | Start with open 0.5–3B same-family continuation checkpoints, then OLMo and representative UpgradeBench tasks (e.g. intent, structured output, text-to-SQL). Three or more release boundaries; interleave new, revised, and revoked skills. Evaluate unrelated prompts, paraphrases and overlapping intents. Include cross-family transfer as a separate stress test. | The effect vanishes when the old checkpoint is genuinely unavailable, a budget-matched teacher snapshot is just as good, or the method has to reject most deployments. |

**Baselines and ablations.** New base; raw copy; task arithmetic and TIES/DARE for compatible bases; retained LoRA bank with learned and oracle routing; feature bridge/Procrustes; random saved teacher logits + identical solver/router; nearest-neighbor and uncertainty-based probe selection; legacy-teacher replay when available; LoRA refit with original labels and offline joint training as privileged references. Ablate counterfactual pairs, negative witnesses, open-set routing, source retirement, bytes and rank. Run same probes and candidate search budget, count rejected and failed installs, and separate regimes where methods need unavailable inputs.

**Metrics.** Report final mean and worst-skill retention, backward transfer relative to acquisition, new-skill learning, performance vs release-native base, revoked and untouched domain flips, unsupported-input patch activation, risk–coverage curves, false reject rate, bytes (including probe bank, router, and deployed adapters), GPU hours, and latency. Set threshold on validation lineages then freeze; bootstrap release/task units (not independent prompts from the same checkpoint). Pre-register five-point skill and two-point unrelated-accuracy harm windows as initial targets subject to task-specific variance, and report sensitivity. Keep test labels in an evaluator never queried for install/tuning.

**Go/no-go.** Require at least 60% coverage and a 30% relative reduction in harmful accepted upgrades over random saved logits at matched coverage, plus no loss of worst-skill retention, on held-out CPU/vision trajectories with enough failures for meaningful intervals. Treat these as design targets, not guarantees. At language scale, require replicated gains on two independent families or narrow the claim to the supported regime. If probe selection fails to add value after two pre-specified variants and fair replay controls, stop expanding model size, write up the negative, and move to procedural regeneration. If a near-free router or random replay solves the tasks, the benchmark is too weak.

## How to execute

1. **First week, CPU:** Reproduce the included pilots. Freeze dataset splits, a release/edit event schema, labeled scoring, and metrics before trying additional algorithms. Add controlled collision cases and alternate domain orders. Make each run emit provenance, budgets, methods, admissions and labeled scores to machine-readable files. Iterate on validation lineages only.
2. **Second milestone, one GPU:** Budget roughly 40–100 GPU-hours for vision and 0.5–3B proof of feasibility, using cached forward features where valid, fixed seeds, and benchmarked wall-clock pilots. Stage source snapshots only at acquisition; assert that migration jobs cannot read them. Run matched-cost replay and weak/strong router controls before any large sweep.
3. **Cluster gate:** Only after the small-model go criteria, request 4–8 A100/H100-class GPUs for independent 3–8B PEFT jobs, roughly 300–800 GPU-hours pending profiling. Use mixed precision and cached audit inference, store lineage/checkpoint manifests and separate access to gold scoring; parallelize by lineage and seed, not by changing the experiment. No full pretraining required.
4. **Submission milestone:** Lock hypotheses, run blind release chains and ablations, and reproduce from a clean environment. Release the harness, manifests, and failure cases. A NeurIPS/ICLR submission needs either replicated new capability with a clear mechanism and matched controls, or a compelling impossibility/failure result that changes how people evaluate continual specialization. The CPU results alone are neither.
